## Kubernetesクラスターとは

**クラスター** = 複数のマシンをまとめて1つのシステムとして動かすもの

### 普通のサーバー vs クラスター

```
普通のサーバー：
┌─────────┐
│ マシン1台 │  ← 1台で全部やる
└─────────┘

クラスター：
┌─────────┬─────────┬─────────┐
│ マシンA  │ マシンB  │ マシンC  │  ← 複数台をまとめて管理
└─────────┴─────────┴─────────┘
        ↑
    これ全体で「クラスター」
```

### Kubernetesクラスターの構成

```
┌─────────────────────────────────────┐
│       Kubernetesクラスター            │
│                                     │
│  ┌───────┐  ┌───────┐  ┌───────┐   │
│  │ Node1 │  │ Node2 │  │ Node3 │   │  ← Node = マシン
│  │       │  │       │  │       │   │
│  │ Pod   │  │ Pod   │  │ Pod   │   │  ← Pod = コンテナ(アプリ)
│  │ Pod   │  │ Pod   │  │       │   │
│  └───────┘  └───────┘  └───────┘   │
│                                     │
│  Kubernetesが「どのマシンで何を動かすか」│
│  を自動で決めてくれる                   │
└─────────────────────────────────────┘
```

### 1つのクラスターで複数のサービスを管理する

Kubernetesはコンテナ1つに対して1つ用意するものではない。
**1つのクラスターが、異なる複数のサービスをまとめて管理する。**

```
┌─────────────────────────────────────────┐
│         Kubernetesクラスター（1つ）        │
│                                         │
│  ┌─────────────┐    ┌─────────────┐     │
│  │ 画像処理API   │    │  認証サーバー  │     │
│  │  Pod Pod Pod │    │  Pod Pod    │     │  ← 別々のアプリ
│  │  (3つに増やす) │    │  (2つで十分)  │     │
│  └─────────────┘    └─────────────┘     │
│                                         │
│  Kubernetesが両方まとめて面倒を見る          │
│  - 画像処理APIは負荷高い → Pod増やす        │
│  - 認証サーバーは軽い → 少なめでOK          │
└─────────────────────────────────────────┘
```

サービスごとに別の Deployment を書いて、同じクラスターにデプロイするだけ。
実際の現場では1つのクラスターに何十ものサービスが同居しているのが普通。

このプロジェクトでは画像処理APIだけだが、仕組みは同じ。

### Kubernetesを使う状況・使わない状況

**使う場面：**
- ユーザー数が数万〜数百万規模で、サーバー1台では処理しきれない
- アクセスに波がある（例：セール時にアクセス10倍）→ 手動でサーバー増減してたら間に合わない
- サービスが落ちたら困る → サーバー1台だとそれが死んだら全滅

**不要な場面：**
- 社内ツールでユーザー数十人 → サーバー1台で十分
- 個人開発やアクセスが少ないサービス → VPS1台やPaaSで事足りる

**使う決め手は「手動管理の限界」：**
- サーバー2〜3台なら手動でもいける
- 10台超えてくると「どのサーバーにどのアプリを置くか」「落ちたらどうする」「増やすタイミングは」を人が管理するのがつらくなる → Kubernetesに任せたい

## NodeとPodの違い

シンプルに言うと：

```
Node = パソコン（マシン）
Pod  = アプリ（プログラム）
```

### 例え

```
あなたのPC（Node）
├── Chrome（Pod）
├── Slack（Pod）
└── VS Code（Pod）
```

1台のパソコンで複数のアプリを動かすのと同じ。

### Kubernetesでの図

```
┌─────────────────────────────────────────┐
│            Kubernetesクラスター           │
│                                         │
│  ┌─────────────┐    ┌─────────────┐    │
│  │   Node A    │    │   Node B    │    │  ← マシン（サーバー）
│  │  (マシン)    │    │  (マシン)    │    │
│  │             │    │             │    │
│  │ ┌───┐ ┌───┐│    │ ┌───┐      │    │
│  │ │Pod│ │Pod││    │ │Pod│      │    │  ← アプリ（コンテナ）
│  │ └───┘ └───┘│    │ └───┘      │    │
│  └─────────────┘    └─────────────┘    │
│                                         │
└─────────────────────────────────────────┘
```

### このプロジェクトの場合

```
Node（minikubeが作った仮想マシン）
├── Pod（画像処理API）
├── Pod（画像処理API）  ← 同じアプリを複数起動できる
└── Pod（画像処理API）
```

### 比較

| | Node | Pod |
|--|------|-----|
| 何？ | マシン（サーバー） | アプリ（コンテナ） |
| 例え | パソコン本体 | Chrome, Slackなどのアプリ |
| 増やすと？ | サーバー台数が増える | 同じアプリのコピーが増える |

Kubernetesは「どのNode（マシン）にどのPod（アプリ）を配置するか」を自動で管理してくれる。

## コンテナとPodの違い

### シンプルな理解

```
コンテナ ≒ Pod（ほぼ同じと思ってOK）
```

このプロジェクトでは、1つのPodに1つのコンテナだけ入ってるから、同じものと思って大丈夫。

### 厳密な違い

```
Pod = コンテナを入れる「箱」
コンテナ = 実際のアプリ

┌─────────────────┐
│      Pod        │  ← Kubernetesが管理する単位
│  ┌───────────┐  │
│  │ コンテナ   │  │  ← 実際に動くアプリ（Docker）
│  └───────────┘  │
└─────────────────┘
```

### なぜ分かれてるの？

1つのPodに複数のコンテナを入れることもできる：

```
┌─────────────────────────┐
│          Pod            │
│  ┌─────────┐ ┌───────┐  │
│  │ メインAPI │ │ログ収集│  │  ← 2つのコンテナが協力して動く
│  └─────────┘ └───────┘  │
└─────────────────────────┘
```

でも普通は「1 Pod = 1 コンテナ」で使うことが多い。

### 比較

| | コンテナ | Pod |
|--|---------|-----|
| 何？ | Dockerで作ったアプリ | コンテナの入れ物 |
| 誰が管理？ | Docker | Kubernetes |
| 数 | 1つのPodに1つ以上 | 通常は1対1 |

**初心者のうちは「Pod = コンテナ」と思っておけばOK。**

## minikubeとは

学習用に、自分のPC内でKubernetesを動かすツール。

### 本番環境（会社とか）

お金を払って複数のサーバーを借りる：

```
AWS/GCPのサーバー（月額数万円〜）
┌─────────┐  ┌─────────┐  ┌─────────┐
│サーバー1 │  │サーバー2 │  │サーバー3 │
└─────────┘  └─────────┘  └─────────┘
```

### 学習するとき

サーバー借りるのはお金かかる。だから自分のPC内で練習したい。

```
あなたのPC
┌─────────────────────────┐
│                         │
│  minikube（無料）        │
│  ┌───────────────────┐  │
│  │ 仮想的なサーバー     │  │  ← 本物じゃないけど同じように動く
│  │  Pod  Pod  Pod    │  │
│  └───────────────────┘  │
│                         │
└─────────────────────────┘
```

### 比較

| | 本番 | 学習 (minikube) |
|--|------|----------------|
| サーバー | 複数台（有料） | PC内に仮想で作る（無料） |
| 使うコマンド | 同じ `kubectl` | 同じ `kubectl` |
| 学んだことは？ | - | そのまま本番で使える |

minikubeで練習したことは、そのまま本番環境でも使える。だから学習に便利。

## Goの並行処理とKubernetesの違い

### Goの並行処理（goroutine）

**1台のサーバー内**で複数リクエストを同時処理。

```
サーバー1台
├── リクエストA → goroutine → 処理中...
├── リクエストB → goroutine → 処理中...
└── リクエストC → goroutine → 処理中...
```

- 1台のCPU/メモリを効率的に使う
- でも1台の限界がある（CPU100%になったら終わり）

### Kubernetesのスケーリング

**サーバー自体を増やす**。

```
Pod 1（サーバー1台目）
├── goroutine → 処理中...
├── goroutine → 処理中...

Pod 2（サーバー2台目）← Kubernetesが増やした
├── goroutine → 処理中...
├── goroutine → 処理中...

Pod 3（サーバー3台目）← Kubernetesが増やした
├── goroutine → 処理中...
```

### 比較

| | Goの並行処理 | Kubernetes |
|--|-------------|------------|
| 何を増やす？ | 処理スレッド | サーバー台数 |
| 範囲 | 1台のマシン内 | 複数マシン |
| 限界 | マシンのスペック | 事実上なし |
| 障害時 | サーバー落ちたら全滅 | 他のPodで継続 |

**両方組み合わせて使う**：
1. 各サーバー内ではgoroutineで効率的に処理
2. サーバー1台で足りなくなったらKubernetesがPodを増やす

## Makefileとは

よく使うコマンドをまとめたショートカット集。

### 使用例

```bash
# 普通にやると長い
go run ./cmd/api

# Makefileがあれば短く書ける
make run
```

### このプロジェクトのコマンド

```bash
make run              # サーバー起動
make build            # バイナリビルド
make load-test        # 負荷テスト

make docker-build     # Dockerイメージビルド
make docker-run       # Dockerコンテナ起動

make k8s-apply        # Kubernetesにデプロイ
make k8s-delete       # Kubernetesから削除
make k8s-status       # 状態確認
make k8s-logs         # ログ確認
```

## シェルスクリプト(.sh)とは

ターミナルで実行するコマンドをファイルにまとめたもの。

### 例

手で100回コマンドを打つのは大変：
```bash
curl -X POST -F "image=@sample.jpg" "http://localhost:8080/api/resize"
curl -X POST -F "image=@sample.jpg" "http://localhost:8080/api/resize"
curl -X POST -F "image=@sample.jpg" "http://localhost:8080/api/resize"
# ... 100回
```

スクリプトにまとめれば一発：
```bash
./scripts/load-test-image.sh http://localhost:8080 10 100
```

### 実行方法

```bash
# 直接実行
./scripts/load-test-image.sh

# または bash で実行
bash scripts/load-test-image.sh
```

### このプロジェクトのスクリプト

| ファイル | 役割 |
|---------|------|
| `load-test-image.sh` | 負荷テスト（大量リクエスト送信） |
| `load-test.sh` | 軽い負荷テスト（/health だけ） |
| `watch-pods.sh` | Pod の状態をリアルタイム監視 |

### Makefileとの違い

| | Makefile | シェルスクリプト |
|--|----------|----------------|
| 書き方 | `make xxx` | `./scripts/xxx.sh` |
| 用途 | 短いコマンドのショートカット | 複雑な処理（ループなど） |
| 例 | ビルド、起動、デプロイ | 負荷テスト |

## 用語集

| 用語 | 意味 |
|------|------|
| **Pod** | Kubernetesで動くコンテナの最小単位。1つのアプリ。 |
| **Node** | Podが動くマシン（サーバー）。 |
| **Cluster** | 複数のNodeをまとめたもの。 |
| **Deployment** | Podの数や更新方法を管理する設定。 |
| **Service** | Podへのアクセス方法を定義。ロードバランサー的な役割。 |
| **ConfigMap** | 設定値を外部ファイルで管理。 |
| **Secret** | パスワードなど機密情報を管理。 |
| **HPA** | Horizontal Pod Autoscaler。負荷に応じてPod数を自動調整。詳しくは [orchestration-and-hpa.md](orchestration-and-hpa.md) |
| **kubectl** | Kubernetesを操作するコマンドラインツール。 |
| **minikube** | ローカルPCでKubernetesを動かすツール。 |
| **Docker** | コンテナを作成・実行するツール。 |
| **コンテナ** | アプリとその依存関係をパッケージ化したもの。 |
| **イメージ** | コンテナの元になる設計図。Dockerfileから作る。 |
